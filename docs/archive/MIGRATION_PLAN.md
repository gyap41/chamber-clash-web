### run_tests.ps1が実際には動かなかった問題と、その解決

本セッションはユーザー環境のGodot実行ファイルへコマンドを直接実行する手段を持たないため、上記の実装は前回コード上のレビューのみで確定し、ユーザー側でrun_tests.ps1を使って実行確認する運びとしていた。ここから実際に全PASSを確認するまでに、以下の問題が順に見つかり、その都度修正した。

1. **文字コード**：run_tests.ps1が非BOM UTF-8で保存されていたため、日本語コメントを含む状態でWindows PowerShell 5.1が既定のANSIコードページ（Shift-JIS）として誤読し、構文エラーになっていた。スクリプト全体を英語/ASCIIへ書き直して解消。
2. **ファイル転送の信頼性**：上記の修正をdevice_commit_filesでユーザー環境へ書き込んだ際、ツールは成功を報告したにもかかわらず、実際には反映されていないケースが複数回（本セッション中に4回以上）発生した。以後、コミット直後に必ずファイルを再取得して内容とバイト数を突き合わせ、一致を確認してからユーザーに再実行を依頼する運用に変更した。
3. **0 passesで全FAIL**：文字コード問題を解決した後も全10テストが0 passesでFAILし続けた。原因はGodotの通常配布物（`Godot_v4.7.2-stable_win64.exe`）がWindows上でGUIサブシステムのバイナリであり、標準出力・標準エラーをリダイレクトしても内容が一切届かないこと（`--headless`指定でも同様）。Godot公式配布ZIPには同梱でコンソールサブシステム版（`Godot_v4.7.2-stable_win64_console.exe`、実体は同フォルダの本体exeを見つけて起動する薄いラッパー）が含まれており、これを取り出して`.local/tools/`内の本体exeの隣に配置し、run_tests.ps1が本体exeの隣に`_console.exe`があれば自動的にそちらを使うよう修正した。
4. **1件目で全体が止まる**：上記を解決すると、equipmentテストの実行中にGodotが書いたログ行（`SCRIPT ERROR: Assertion failed.`）がstderr経由でPowerShellのErrorRecordとなり、`$ErrorActionPreference = "Stop"`により即座に致命的エラー扱いされ、スクリプト全体がそこで中断していた（以降の9ファイルが未実行のまま要約に表示される状態）。テストループの実行中だけ`$ErrorActionPreference`を"Continue"に変更して解消。

上記をすべて解決したところで、equipment/pulse/relics/relics2の4ファイルで本物のテスト失敗が判明した。原因はゲームロジックの不具合ではなく、レリック12種を全て解放したことで、既存テストがハードコードしていた前提が崩れたこと：

- equipment.gd・pulse.gd：「レリックID2（プリズムレンズ）は未実装だから購入できないはず」という前提で書かれていたブロック確認が、実装済みになったことで購入が成立してしまうようになっていた。オファーの価格を購入不可能な額（500CR）へ変更し、「ブロックされて資金が減らない」という検証の意図自体は維持した。
- relics.gd：(a) ショップ候補IDの範囲チェックが旧SUPPORTED（`[0,1,4]`）のままハードコードされていたため、全12種の範囲（`range(0,12)`）に修正。(b) 「未実装レリックは取得できない」確認にレリックID2を使っていたが、2が実装済みになったため、カタログ範囲外のID（12）を使う形に変更（ガード自体の動作は変わらない）。
- relics2.gd（今回新規作成）：(a) 共通のsetup()ヘルパーが両プレイヤーへ武器ID1をショップで既に付与済みであるにもかかわらず、予備マガジンのテストで同じID1をもう一度add_gun()しようとしていた誤り（既に所持している武器は追加できない仕様のため失敗する）。冗長な呼び出しを削除。(b) main.gdの遅延ショット（delayed_shots）にスターターセル対応で新設した"damage"キーを、pulse.gd側が手動で組み立てているテスト用データが持っておらず、存在しないキーへのアクセスでクラッシュしていた。該当箇所へダミー値を追加して解消。

### (1) 立ち絵が表示されない

### (2) カードが画面外にはみ出す

`button.clip_text = true`と`button.text_overrun_behavior = TextServer.OVERRUN_TRIM_ELLIPSIS`を設定し、ボタンの実測幅を常に`custom_minimum_size`（245×150）に固定した。4列合計は245×4＋separation8×3＝1004pxとなり、画面幅1120px・Panelの利用可能幅（約1040px）のいずれにも収まる。カード本文は名前・役割・HP・速度のみへ簡略化し、装填時間倍率・回避クールダウン・初期パルス回数を含む全文はButton.tooltip_textへ移した（ホバーで確認可能。weapon_catalog系のカードで`button.tooltip_text = g.desc`としているのと同じパターン）。

## 2026-09-08 CPU対戦の実装（M3最後の項目）

### 元Webの参照箇所

legacy-web/dist/game.jsのaiInput()（P2固定、P1固定敵）とupdatePlayer()のCPU分岐（`p.id===1 && mode==='cpu'`でaiInput()を呼ぶ）を読み、以下の要素を確認した：照準ジッター（`sin(elapsed*2.2)*.09`）、武器が完全に空の場合の自動切替、補給品の優先探索（弾薬/レリック/武器の種別ごとの欲しさ判定、Sレア武器はコストを0.65倍して優先）、距離ベースの接近(340px超)/後退(200px未満)/その間の横移動（`sin(elapsed*.7)*.8`）、危険地帯回避（実ダメージ判定+25pxより広い+65/+60pxマージンでアリーナ中心へ）、被弾回避（90px以内の敵弾へ垂直操舵、ランダム0.35〜0.75秒クールダウンで実際のロール発動）、パニックパルス（120px以内に敵弾6発超で使用）、障害物回避（±90度/180度の候補角度）、リロード自動化、64px以内での近接自動発動、射撃判断（射線が壁で遮られていない、または跳弾・ブーメラン武器なら遮られていても撃つ）。あわせてlegacy-web/dist/shop.jsのselectGun()/readyShop()のmode==='cpu'分岐（P2の武器ドラフト・ショップ購入をP1の操作完了と同時に自動処理し、P2の画面自体を出さない）も確認した。

### 実装

- **scripts/cpu_ai.gd**（新規）：`static func decide(game, player, enemy, dt) -> Dictionary`の単一エントリポイント。移動方向(dx,dy)・射撃可否・照準ジッターを辞書で返す一方、武器切替・リロード開始・ロール・近接・パルス使用・補給取得といった副作用は元Webのaiインプット同様その場で直接プレイヤー/ゲームへ適用する。
- **player.gd**：`is_cpu`フラグ（既定false、char_idと同じくreset_round()を跨いで保持）を追加。`step(dt, i, enemy, arena, mouse_shooting, ai: Dictionary = {})`に`ai`引数を追加し、非空の場合はInputを一切参照せず`ai.dx/dy`（正規化前、updatePlayer共有の正規化ステップに合わせる）・`ai.aim_jitter`・`ai.shoot`をそのまま使う。stateに`ai_cd`（被弾回避ロールのクールダウン、初期値`randf_range(.25,.6)`）を追加。
- **main.gd**：`CpuAI.decide(self, players[i], players[1-i], dt)`を`is_cpu`なプレイヤーについてのみ毎物理フレーム呼び、step()へ渡す。P2用のキー入力ハンドラ群（矢印移動、J/K/L/P/O/H、1〜4装備は元々P1専用）は`is_cpu`のプレイヤーをスキップする。
- **hud.gd**：ステータス文字列にCPU側は「P2 (CPU)」を表示し、操作ヒント行をCPU側では「P2はCPUが自動操作」に置き換える。武器枠ボタンの無効化条件へ`player.is_cpu`を追加し、CPU側の枠クリックによる装備変更を防ぐ。
- **scenes/character_select.tscn / character_select.gd**：Panel/Content先頭にLocal/CPU切替ボタン（ModeRow、`toggle_mode=true`の2ボタン）を追加。`cpu_mode`が立っている状態でP1（`char_turn==0`）がキャラを選ぶと、P1と異なるキャラからP2をランダムに選出し即座に`start_match()`（P2のカード選択画面自体をスキップ）。`game.players[1].is_cpu = cpu_mode`をstart_match()内で設定。
- **preparation.gd**（スコープ拡張、下記参照）：select_gun()・ready_shop()にCPU自動完了分岐を追加。

### スコープ拡張についての明記

CPU対戦を実際にプレイ可能にするには、preparation.gd（武器ドラフト・ショップ画面）の変更が追加で必要だと実装中に判明した。理由：CPU対戦ではP2が画面操作をする機会自体がないため、preparation.gdを無変更のままだと、CPUを選んだ時点でゲームが"draft"フェーズ（P2の初期武器選択待ち）または"shop"フェーズ（P2のショップ準備完了待ち）で永久に止まり、対戦が開始できない。これはユーザーから個別に指示された変更ではないが、「CPU対戦を実装する」という指示の遂行に不可欠な範囲として、元WebのselectGun()/readyShop()のCPU分岐をそのまま移植する形で追加した。

- `select_gun(id)`：P1（turn 0）が武器を選び、`game.players[1].is_cpu`が真なら、その場でP2へ同じ3候補(`choices`)から`pick_random()`で1丁を追加し、`game.phase = "shop"`へ直接進む（P2はturnを一度も持たない）。
- `ready_shop()`：P1（turn 0）が準備完了した瞬間、`game.players[1].is_cpu`が真なら、`[0,1]`（B/A武器オファー、`offers[2]`のSレアは対象外）のうち`block_reason(1,i)==""`なものから`pick_random()`で1丁購入、`[3,4]`（レリックオファー、`offers[5]`の予備パルスは対象外）のうち購入可能なものから1点購入（いずれも候補が0件なら購入しない）、`shop_ready[1]=true`をセットし、即座に`game.launch_round()`を呼んでP2のショップ画面自体を出さない。
- `refresh()`の表示文言もCPU対戦向けに調整：ショップの案内文をCPU対戦時は「CPU（P2）は自動で購入します。」に、準備ボタンの文言をP1のみの操作で完結する旨に変更。

### 意図的な簡略化・非再現部分

- 元Webはタイマー類（近接・回避・ロール・リロード等）の減算をupdatePlayer()冒頭、aiInput()呼び出しより前に行うため、同一フレーム内でクールダウンがちょうど0になった瞬間から即座に使用可能になる。本移植ではmain.gdがCpuAI.decide()をPlayer.step()（タイマー減算を持つ）より先に呼ぶ構成上、その場合は次の物理フレームまで持ち越しになる（1/60秒程度の遅延、ゲームプレイ上体感できる差ではないと判断）。decide()をPlayer.step()の内部タイマー管理と重複させない、純粋な判断関数として保つための割り切りで、cpu_ai.gdの冒頭コメントに明記した。
- P1の操作方式（左クリック常時自動照準）はこのGodot版が元Webから既に意図的に変更している箇所（2026-09-07「左クリック射撃と次の移行順序」参照）で、CPU対戦の追加にあたってもこの既存の差分は変更・巻き戻ししていない。元WebはCPUモードのP1はマウス照準+クリック発射、ローカル対戦のP1は自動照準+Fキーと操作方式そのものが切り替わるが、このGodot版はモードに関わらずP1が常に自動照準+左クリックのままである。

### 実機確認で判明した全テストFAILとその修正

上記コミット後、ユーザーが実機でrun_tests.ps1を実行したところ、CPU対戦と無関係なsmoke/equipment/pulse/relics等を含む全14テストファイルが0 passesでFAILした。ユーザー環境の`.local/logs/run_tests-20260908-163313.log`を取得して調査。

根本原因はGDScriptの静的型推論エラー2箇所（実質4行）だった：

1. **scripts/player.gd:112**（今回のstep()改修箇所）：`var shooting := ai.shoot if not ai.is_empty() else (mouse_shooting if i == 0 else Input.is_physical_key_pressed(KEY_J))`。`ai`はDictionaryのため`ai.shoot`は型なしVariantとして扱われ、もう一方の分岐（bool）と型が一致しないため`:=`での型推論に失敗し、`Parse Error: Cannot infer the type of "shooting" variable`でGDScriptのロード自体が失敗した。player.gdはPlayerシーンのスクリプトであり、ほぼ全テストがPlayerノードを介するため、ロード失敗時にPlayerノードがスクリプトなしの素の`Node2D`にフォールバックし、以降`state`/`char_id`/`is_cpu`/`add_gun`/`reset`/`set_character`等へのアクセスが軒並み失敗する形で、無関係な既存テストも含め全滅する連鎖障害になっていた。
2. **tests/cpu_ai.gd**（今回の新規テスト）：同種のパースエラーが3箇所（`to_center`＝`Vector2(560,300)-p.state.pos`、`to_s`＝`item_s.position-p.state.pos`、`to_item`＝`ammo_item.position-p.state.pos`）。いずれもDictionaryのキーやVariant型変数どうしのVector2引き算の結果を`:=`で受けており、同じ理由で型推論に失敗していた。

4箇所とも`var x := ...`を`var x: 型 = ...`という明示的な型注釈へ変更し（shooting: bool、to_center/to_s/to_item: Vector2）、型推論に頼らない形にして解消した。この種のエラーはGDScriptの静的型推論の実際の挙動（Dictionary経由のアクセスが常にVariant扱いになること）に依存するため、コードレビューだけでは事前に気づけず、ユーザーの実機実行で初めて判明した。修正版は再コミット・再取得によるバイト照合済みで、ユーザーへ再実行を依頼中。

### 型推論エラー修正後、cpu_aiのみFAILした問題とその修正

ユーザー環境で再実行した結果、パースエラーは解消しcpu_ai以外の13ファイル全てがPASSした。cpu_aiのみ`res://tests/cpu_ai.gd:37`のassert失敗でFAILし、ログ（`.local/logs/run_tests-20260908-181239.log`）を取得して調査した。今回はGDScriptの型推論ではなく、テストのシナリオ設計そのものにランダム性への配慮漏れがあった。

`enter_play()`ヘルパーは`game.preparation.choices[0]`（`preparation.gd`の`begin()`がB武器プールをシャッフルして選ぶ、実行のたびに変わるランダムなID）をP1・P2双方の武器ドラフトにそのまま渡す。武器自動切替のサブテスト（37行目）は`p.add_gun(1)`（跳弾キャンディをID固定で追加）を前提にしていたが、`choices[0]`がたまたまID1と一致した実行では、P2は既にドラフトでID1を所持しており、`add_gun()`の所持済みチェックに引っかかって`false`を返し、assertが落ちた。さらに続く射撃判断のサブテストも`p.equip_slot(1)`（インベントリのスロット1）を跳弾キャンディだと決め打ちしていたが、スロット1の中身は実際にはドラフトでP2が受け取ったランダムな武器であり、跳弾キャンディとは限らない別の潜在バグだった（`choices[0]==1`の実行でしか偶然成立しない、隠れた依存関係）。

修正は次のとおり。武器自動切替側は、既知の実装済みID候補リストから「まだ所持していないID」を動的に選んで追加する方式に変更（候補が尽きることは実質ないが、念のためassertで保証）。射撃判断側は、インベントリをID1で検索し、既に所持していればそのインデックスを使い、無ければその場で追加してそのインデックスを使う方式に変更し、スロット番号への決め打ちをやめた。これによりドラフトのランダムな抽選結果に関わらず決定的に振る舞うテストになった。

### 続けて判明した3件目：サブテスト間のタイマー残留

上記を修正して再実行したところ、今度は`res://tests/cpu_ai.gd:150`（近接自動発動の`assert(p.state.melee > 0.0)`）でFAILした。これも実装側ではなくテスト側の見落とし。手前の被弾回避サブテストが`p.state.ai_cd`を強制的に期限切れにして実際の回避ロールを発生させており、これは`handle_key()`内部で`state.roll = dodge_duration`をセットする。通常のプレイでは毎フレーム`Player.step()`がタイマー類（roll/reload/melee等）を`maxf(0, x-dt)`で減算していくためすぐに0へ戻るが、`tests/cpu_ai.gd`は`Player.step()`を経由せず`CpuAI.decide()`を直接呼ぶだけの単体テストなので、`state.roll`はセットされた値のまま以降ずっと正の値で残留する。近接自動発動を許可する`handle_key()`の`p.roll <= 0`ガードにこれが引っかかり、近接テストの時点で近接が発動しなかった。

近接テスト直前で`p.state.reload`を明示的にリセットしているのと同じ箇所・同じ理由で、`p.state.roll = 0.0`も追加でリセットするようにした。型推論のパースエラー（1件目）、ドラフトのランダム性への配慮漏れ（2件目）に続き、これで3回連続、`CpuAI.decide()`を直接呼ぶ単体テストという構造そのものに起因する見落とし（Player.step()が本来担っているタイマー減算が起きないこと）が見つかったことになる。

### 続けて判明した4件目：補給品の取得待ち時間（pickup_delay）

再度修正して再実行したところ、今度は`res://tests/cpu_ai.gd:187`（補給品取得の`assert(p.inventory[0].reserve > 1)`）でFAILした。`scripts/supplies.gd`の`acquire()`は`item.age < pickup_delay`（既定0.6秒、README「フィールド補給」の「出現0.6秒後から取得可能」に対応）の間は取得自体を拒否する。`item.age`は通常`main.gd`の`_physics_process`経由で毎フレーム`supplies.gd`のtick処理が加算するが、このテストは`CpuAI.decide()`を直接呼ぶだけで一切フレームを進めないため、`put_item()`で生成した補給品の`age`は常に0のまま、`decide()`内部の`game.supplies.acquire(1,target,force)`呼び出しが毎回拒否されていた。
